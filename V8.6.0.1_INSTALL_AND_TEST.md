# Workday Journey V8.6.0.1 - Cloud Sync & Bank Hotfix

## Install order (important)

1. Back up the existing site files. Before replacing the app, use Settings > Export Backup on devices that still have historical Local-only Work Bank savings. **Do not clear browser site data.**
2. In Supabase SQL Editor, run **`SUPABASE_BANK_HOTFIX_V8.6.0.1.sql`** once as a project administrator. Prerequisites: V8.5.0.1 Economy Security and V8.6.0 Guest-to-Cloud SQL have already been applied.
3. Confirm SQL executed without errors. The SQL is re-runnable; it creates `work_bank_accounts`, `work_bank_transactions` and the `get_my_bank` / `bank_move_secure` RPCs and permissions.
4. Copy the changed site files to the **same project root** as V8.6.0. Keep all unchanged files in place. Deploy/update the site.
5. Reload with Ctrl+Shift+R (or Clear App Cache / Reload Latest Version if using PWA). Sign in again if needed.
6. Test with a **test account** before depositing real accumulated Work Coins.

## Why this is required

Before V8.6.0.1, signed-in users deposited coins only into LocalStorage. The wallet is server-authoritative and loaded its earlier amount back, so a deposit could appear to reverse. In this patch, signed-in deposits and withdrawals use an atomic database operation that updates both wallet and Savings. The browser cannot set its own server balance.

Guest mode still uses the old Local-only Work Bank and does **not** import its balance to Cloud. Cloud Savings now comes strictly from `work_bank_accounts`.

**Historical Local-only Savings are not automatically transferred to Cloud.** If a returning Cloud user had previous local deposits, the old device-only ledger is preserved as a backup (also in `wdj-v8601-guest-bank-backup` on that browser). The Cloud Bank may initially show zero. A trusted Owner should verify historical Wallet transactions and prior Bank data before any manual correction. Do not run an anonymous automatic migration from LocalStorage; that would reintroduce the coin exploit.

Do **not** delete a user's account just to resolve balance mismatches. Do not clear user LocalStorage until previous Bank history has been reviewed and backed up.

## Change summary

- `SUPABASE_BANK_HOTFIX_V8.6.0.1.sql` (new) - Protected bank accounts and ledger, daily interest (Bangkok time), once-per-day compounding, atomic/idempotent deposit/withdraw, read-only RLS policies for users.
- `v8601.js` (new) - Bank RPC bridge with short-lived cache, one in-flight fetch, account isolation, stale-response protection, and Guest savings backup/restore.
- `v8601.css` (new) - Loading/retry state and legacy Local savings warning.
- `v81.js` - Guest keeps Local banking; signed-in users cannot deposit/withdraw until secure Bank RPC is ready. It never computes/credits Cloud interest locally.
- `v8.js` - Reduces repeated Cloud reconciliation from overlapping auth events and focus changes; skips uploads when no payload changed; excludes page-visit activity from generic Cloud Sync; protects concurrent uploads and account changes.
- `v8501.js` - Deduplicates Coin refreshes, avoids unnecessary render changes and ignores stale fetches after a newer server-verified transaction.
- `index.html`, `service-worker.js`, `v850.js`-`v855.js` - Version and PWA asset updates; What's New entry for 8.6.0.1.

## Test checklist

1. Sign in to a test account with a known **server** Wallet balance (for example 1000 Coins). On Work Bank, the initial Savings is the DB balance.
2. Deposit 300 Coins. The server should now show Wallet 700 and Savings 300 (if starting at 1000/0).
3. Navigate through Dashboard, Journal, Projects, Calendar, Reports. The Cloud indicator should not enter Syncing on *every* route switch just because of the visit.
4. Reload and reopen Work Bank. Wallet/Savings must remain 700/300.
5. Withdraw 100 Coins. Wallet/Savings should be 800/200 after reload.
6. In DevTools, modify `wp-v83-bank-ledger`, reload. The Cloud Savings must still be the server balance.
7. Sign out. The previously saved Guest Work Bank data on the device should return.
8. Try an offline deposit while signed in: it must be rejected and must not mutate Local savings.
9. After a calendar day passes in **Asia/Bangkok** timezone, a Bank read should accrue at most one interest transaction for that date. Repeated reloads on the same day must not credit it twice.
10. Cross-device test: after a successful transfer, another signed-in device must see the new Savings balance when it fetches the Bank RPC. Refresh the other device's Wallet balance if needed.

## Admin-only read-only diagnostics

Run these **separately** in Supabase SQL Editor if you want to inspect state:

```sql
select count(*) as bank_accounts from public.work_bank_accounts;
select kind, count(*) as transactions, sum(amount) as net_amount
from public.work_bank_transactions group by kind order by kind;
select has_function_privilege('authenticated',
  'public.bank_move_secure(text,bigint,uuid)','EXECUTE') as bank_rpc_granted;
```

Never grant INSERT/UPDATE on `work_bank_accounts`, `work_bank_transactions` or `work_coin_accounts` to `authenticated`. They must be changed only through authorized database logic.

## Known limits

- Cloud Bank interest is based on server-day in `Asia/Bangkok`, not user-editable local time. It is computed on Bank RPC requests, so may appear once the user next visits the Bank.
- Guest/local economy remains editable by its own device; only Cloud bank and wallet are protected here.
- Daily Missions, Chests and Work Exchange still contain client-side economy logic. V8.6.1 is planned to move these to server-side authorization.
- No automated historical Local-only Savings migration is provided, intentionally.
- Frontend tests and mocked RPC tests have run; **live Supabase SQL execution and end-to-end integration tests still need to be done in your Supabase project**.
